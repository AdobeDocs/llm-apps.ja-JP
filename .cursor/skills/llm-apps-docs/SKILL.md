# LLM アプリドキュメント

Adobe LLM アプリ用に、タスク指向の検証可能な公開ドキュメントを作成します。

## Source-of-truth注文

次の順序で製品の請求内容を確認します。

1. 現在の実稼動UI （`https://experience.adobe.com/#/@llmapps/llm-apps/`）
2. ワークスペースで利用可能な現在のUIとAPIの実装
3. 現在のパブリック SDKと定型文の動作
4. 既存の公開ドキュメント

実稼動がソースまたは計画と競合する場合は、実稼動を文書化し、不一致を報告します。 現在利用可能なワークフローを公開しないでください。

## すべてのタスクを開始

1. `help/main-toc/TOC.md`をお読みください。
2. ターゲット記事と直接関連する記事を読む。
3. [content-model.md](content-model.md)を使用してコンテンツを分類します。
4. 検証が必要なUI ラベル、URL、コマンド、およびコントラクトを識別します。
5. ページをまたいで、サンプルと用語の一貫性をエンドツーエンドで維持できます。

## オーサリングルール

- アプリの自動作成（**[!UICONTROL アプリを自動的にビルド]** フロー）を通じて、初めてのユーザーをリードします。
- 実装のトピックではなく、ユーザージャーニーと結果に関するナビゲーションを整理します。
- 各ガイドの開始付近にジャーニーの順序を記載し、次の共有ステップを提示します。
- 顧客向けドキュメントでは、内部コードネーム（例えば、「オンボーディングエージェント」）を使用しないでください。この機能は、製品UIでは公開されません。 一般的な説明（例：「プラットフォーム」）を入力し、**[!UICONTROL 自分のアプリを自動的にビルド]**&#x200B;などの正確なUI コピーを使用してコントロールします。
- [!DNL Adobe LLM Apps]はプラットフォームに依存しません。MCP サーバーは、[!DNL ChatGPT]だけでなく、サポートされている任意のLLM プラットフォームで動作します。 [!DNL ChatGPT]が唯一のターゲットであるかのように一般的または例示的な主張を言わないでください（例えば、「ChatGPT」のみよりも「サポートされている[!DNL ChatGPT]のようなLLM プラットフォーム」を好みます）。 [!DNL ChatGPT]の名前を明確に指定できるのは、現在[!DNL ChatGPT]に固有のコンテンツのみです。専用の[ChatGPT ガイド ](/help/guides/test-in-chatgpt.md)でのテスト、その直接のクロスリンク/手続き手順、および[!DNL ChatGPT]に固有の参照またはトラブルシューティングのコンテンツです。
- ユーザーが最初に遭遇したときに技術的なコンセプトを説明します。より深いコンセプトや参考資料にリンクします。
- チュートリアルを直線的に保ち、ハウツーガイドを作成してタスクに焦点を当て、リファレンスページを事実にもとづいて説明します。
- 現在のタスクに必要な情報のみを含め、短く直接的な文章を好みます。
- ジャーニー全体で1つの代表的なアプリを使用します。
- 生成された基礎モードと本番環境での使用に対応した統合を区別。
- 内部ワーカー名、データベースフィールド、実装チケット、不安定なパイプラインの詳細は避けます。
- ガイド間でフィールドテーブルを複製しないでください。参照にリンクします。
- Experience League frontmatterとディレクティブを保持：`[!DNL]`、``、`[!IMPORTANT]`、`[!NOTE]`、および`[!TIP]`。
- ルート相対の内部リンクを使用：`/help/...`。
- 製品ラベルで特に指定されていない限り、タイトルと見出しに文頭の大文字と小文字を使用します。
- 画面と状態を説明する説明的な画像alt テキストを使用します。

## セキュリティ要件

- 資格情報、トークン、プライベート URL、個人データ、内部ホスト名、顧客識別子を含めないでください。
- マネージド設定から読み込まれたシークレットを表示します。ハードコーディングされることはありません。
- 外部サービスにHTTPSが必要です。
- 外部入力とアップストリームの応答を検証する。
- 安全なDOM APIで外部値をレンダリングします。これらを`innerHTML`に補間することはお勧めしません。
- 最小権限のGitHub アプリ、API、CSP、CORS、ブラウザー権限を推奨します。
- 安全なユーザー対応エラーを使用し、機密データのログ記録を回避します。

## スクリーンショットワークフロー

新しい画像または更新された画像については、[screenshots.md](screenshots.md)および[screenshot-manifest.md](screenshot-manifest.md)に従ってください。

デフォルトのワークフローでは、ユーザーが作成した実稼動キャプチャパックが使用されます。

1. `docs-captures/<run-id>/`の下のスクリーンショットを探すか、ユーザーが提供したフォルダーを使用してください。
2. PNG、JPEG、WebPのすべてのファイルをインベントリおよび視覚的に確認します。ファイル名だけを使用しないでください。
3. 表示可能なUI コンテンツを使用して、スクリーンショットをマニフェストの状態に一致させます。
4. ドキュメントを変更する前に、紛失、重複、あいまいな、古い、または安全でないキャプチャを報告します。
5. ソースキャプチャを変更せずに保持します。
6. `help/assets/`の下の安定したマニフェストファイル名を使用して、サニタイズされた最終コピーを作成します。
7. 実際にキャプチャした実稼動ワークフローに合わせて、チュートリアルと関連ガイドを更新します。
8. 正確な代替テキストを追加し、ドキュメント検証を実行します。

エージェントによるブラウザーキャプチャは、オプションのフォールバックのままです。 ブラウザーの状態や資格情報を保存しないでください。また、実稼動で突然変異するスクリーンショットキャプチャをCIで実行しないでください。

「スクリーンショットからドキュメントを更新」するように求められたとき：

- 最新の明示的に選択したキャプチャフォルダーをソースとして扱います。
- アプリのフローやスクリーンショットのマッピングが本当にあいまいな場合にのみ確認します。
- 生のキャプチャフォルダーは絶対にコミットしない。
- 明示的な承認なしに、ソースキャプチャを削除または変更しないでください。
- タスクを不明瞭にせずに機密情報を削除できない場合は、安全な再取得をリクエストしてください。

## Validate（検証）

実行:

```bash
python3 .cursor/skills/llm-apps-docs/scripts/validate_docs.py
```

すべての欠落している内部記事、欠落しているアセット、無効なルート相対パス、欠落しているfrontmatter フィールドを修正してから、作業を引き継ぎます。

また、次の項目も確認します。

- UIのラベルとスクリーンショットは本番環境と一致します。
- スクリプトとウィジェットのURLの例は、ガイドとリファレンスで一致します。
- コマンドは現在のボイラープレートと一致します。
- 新しいページは目次からリンクされています。
- Adobeの記事の検証ワークフローは、使用可能な場合に合格します。
