# 実稼動スクリーンショット手順

次の手順を使用して、実際の公開ドキュメントのスクリーンショットを取得します。

`https://experience.adobe.com/#/@llmapps/llm-apps/`

好ましいワークフローは、人間によるキャプチャの後に、エージェントによる取り込みです。 ユーザーは、関連する実稼動状態を決定します。このスキルは、それらを整理し、サニタイズして、ドキュメントに統合します。

## 受信トレイをキャプチャ

各キャプチャ実行を次の場所に配置します。

```text
docs-captures/<YYYY-MM-DD>/
```

ディレクトリはGitによって無視されます。 生のスクリーンショットはローカルのままにする必要があり、コミットしてはなりません。

ユーザーは任意のファイル名を使用できますが、順序付きの名前を使用すると、レビューが簡単になります。

```text
01-create-app.png
02-connect-github.png
03-onboarding-enabled.png
04-generating-actions.png
05-review-actions.png
```

オプションの`capture-notes.md`は、欠落している状態、通常と異なる動作、または意図する順序を記述できます。

## 安全限界

- Adobe、GitHub、LLM-platformの資格情報をブラウザーで直接入力します。
- MFA、パスキー、キャプチャ、組織の選択、および特権のある同意を停止します。
- トークン、Cookie、ブラウザーストレージ、資格情報の読み取り、印刷、保存、コミットを一切行わない。
- 機密性の低い公開web サイトと、新鮮なドキュメントのみのリポジトリを使用する。
- GitHub Appsに、フィクスチャで使用される2つのリポジトリへのアクセスのみを付与します。
- リポジトリへのアクセスを作成、デプロイ、削除、アーカイブ、または変更する前に確認します。
- 個人情報、組織ID、リポジトリのインストール ID、トークン、または完全なランタイム URLは取得しないでください。

## フィクスチャの命名

使い捨てドキュメントのリソースを明確に識別する名前を使用します。

```text
App: LLM Apps Docs <YYYY-MM-DD>
Handler repo: llm-apps-docs-<YYYYMMDD>
EDS repo: llm-apps-docs-<YYYYMMDD>-eds
```

何かを作成する前に、対象となるAdobeの組織、GitHub オーナー、公開web サイト、フィクスチャ名をユーザーに確認します。

空とプライベートの両方のリポジトリを作成します。 README、ライセンス、または`.gitignore`で初期化しないでください。

## キャプチャ設定

- ブラウザーのクロムを使用せずに完全なダイアログを表示するのに十分な大きさのデスクトップビューポートを使用します。
- ズームを100%に維持します。
- 記事で特にテーマを教えていない限り、デフォルトの製品テーマを使用します。
- タスクと必要なコンテキストを含む最小完了領域をキャプチャします。
- カーソル、ステップとは関係のないオープンメニュー、以前のアクションからのトースト、一時的なスピナーは、スピナーが文書化された状態でない限り避けてください。
- PNGを使用します。
- ファイル名は安定した状態に保ちます。更新時にファイル名を変更する代わりに、画像の内容を置き換えます。

## 推奨キャプチャシーケンス

ユーザーは、以下を含む関連する状態をマニフェストから取得する必要があります。

1. GitHubが接続される前にアプリを作成します。
2. GitHub アプリのリポジトリアクセスの選択。
3. **アプリを自動的にビルド**&#x200B;し、両方のリポジトリを選択して有効にします。
4. アプリ作成またはアプリ構築の自動起動：
5. 生成されるアクション。
6. 生成されたアクションはレビューの準備が整いました。
7. 1つの代表的なアクションのメタデータ、ハンドラー、ウィジェット。
8. アクションごとのレビューと、すべてのアクションがレビューされた状態。
9. ステージングのデプロイメントの成功。
10. アプリ登録とLLM プラットフォームでの代表的な結果。

実際の決定、エラー、前提条件などを説明する画面を追加して撮影します。 あらゆるクリックをキャプチャしないでください。

## スキル受注ワークフロー

ユーザーがキャプチャフォルダーからドキュメントの更新を求める場合：

1. 正確なキャプチャディレクトリを確認します。
2. PNG、JPEG、WebPの各ファイルのインベントリを作成し、各画像を視覚的に調べます。
3. ソースファイルから`screenshot-manifest.md`のエントリへのマッピングを作成します。
4. 表示されるUI ラベルとシーケンスを既存のチュートリアルと比較します。
5. レポート：
   - 必要な状態がありません。
   - 重複または冗長な画像；
   - あいまいな順序；
   - 古いスクリーンショット；
   - 機密情報；
   - ドキュメントと競合する実稼動動作。
6. ソースキャプチャは編集しないでください。
7. 受け入れられる画像ごとに、安定したマニフェストファイル名が`help/assets/guide-onboarding-agent/`の下にあるサニタイズされたコピーを作成します。
8. 切り抜きは、周囲のUIに便利なコンテキストが追加されていない場合にのみ行います。
9. 機密値をマスクします。 安全なマスキングが不可能な場合は、再取得を依頼します。
10. 取り込んだワークフローに合わせて、記事と代替テキストを更新します。
11. リンクとアセットの検証を実行します。
12. ユーザーが明示的に削除を求めるまで、キャプチャフォルダーを配置したままにします。

## オプションのエージェントガイド付きキャプチャ

ユーザーがエージェントにブラウザーの操作を依頼した場合は、同じマニフェストと安全境界を使用します。 認証、特権付き同意、リポジトリの変更、アプリの作成、デプロイメント、クリーンアップのために一時停止します。 この実稼動可変フローを無人で実行しないでください。

## 画像レビュー

すべての画像について：

- 1つのマニフェストエントリに一致させます。
- 記事に対するUI コピーを確認します。
- 不要な場合にアカウントのナビゲーションを切り抜く。
- 個人名、アバター、組織識別子、リポジトリーインストール識別子、ランタイム名前空間、および無関係なアプリをマスクします。
- ブラウザーの自動入力、メール、アクセストークン、プライベートリポジトリーの詳細が表示されていないことを確認します。
- 画面と状態の両方を識別する代替テキストを書きます。

## 停止するタイミング

次の場合にブロッカーを停止して報告：

- ドキュメントに記載されているワークフローと実稼動が一致しません。
- レビューの流れは、公開されたドキュメントとは大きく異なります。
- リポジトリ検証は、意図した空のリポジトリフローを拒否します。
- オンボーディングパイプラインが失敗する。
- 特権アクションには、ユーザーまたは管理者が必要です。
- ステップに不可欠な情報を隠さずにスクリーンショットを安全にすることはできません。
